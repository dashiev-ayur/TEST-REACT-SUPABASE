--------------------------------------------------------------------------------
1. РОЛИ И ОТНОШЕНИЯ
--------------------------------------------------------------------------------
- manager  = "постановщик"  (автор задачи, tasks.author_id)
- executor = "исполнитель"  (назначенный, tasks.assignee_id)
- Глобальная роль хранится в profiles.role (enum user_role).
- "Постановщик"/"исполнитель" в правилах — это ОТНОШЕНИЕ к задаче
  (author_id/assignee_id), а НЕ глобальная роль. Глобальная роль
  используется только для проверки "я manager/executor" и для RLS.

--------------------------------------------------------------------------------
2. ДОСТУП К ОБЪЕКТАМ И ЗАДАЧАМ (матрица прав)
--------------------------------------------------------------------------------
Объекты:
  |            | owner | not owner |
  | manager    | +r+w  | +r-w      |
  | executor   | +r-w  | +r-w      |
  (owner = objects.created_by; executor видит объект, если у него есть
   хотя бы одна задача на этом объекте)

Задачи:
  |            | owner | not owner |
  | manager    | +r+w  | +r-w      |
  | executor   | +r-w  | -r-w      |
  (owner = tasks.author_id; executor видит задачу, если assignee_id = uid)

Принято:
- manager не управляет задачами других manager (RLS update:
  is_manager() AND author_id = auth.uid()).
- executor не редактирует задачи напрямую — только меняет статус через RPC.

--------------------------------------------------------------------------------
3. СМЕНА СТАТУСА: КТО МОЖЕТ СТАВИТЬ КАКОЙ СТАТУС
--------------------------------------------------------------------------------
  | to_status      | Постановщик (author) | Назначенный исполнитель |
  | new            | + (недостижим)       | -                       |
  | in_progress    | -                    | +                       |
  | on_review      | -                    | +                       |
  | accepted       | +                    | -                       |
  | needs_rework   | +                    | -                       |

Принято:
- "new" — только начальное состояние (default при INSERT). Перехода В "new" нет.
- Проверка прав завязана на author_id/assignee_id, НЕ на глобальную роль.

--------------------------------------------------------------------------------
4. ГРАФ ДОПУСТИМЫХ ПЕРЕХОДОВ (очередность)
--------------------------------------------------------------------------------
  new          -> in_progress
  in_progress  -> on_review
  on_review    -> accepted
  on_review    -> needs_rework
  needs_rework -> in_progress

Всё остальное запрещено:
- переход в тот же статус;
- любой переход из accepted;
- "назад" в new;
- needs_rework -> on_review (только через in_progress).

Реализация: is_status_transition_allowed(from, to) — immutable, без прав.

--------------------------------------------------------------------------------
5. ТРИ УРОВНЯ ПРОВЕРОК (не смешивать)
--------------------------------------------------------------------------------
1) Очередность (граф)         — is_status_transition_allowed(from, to)
2) Права на to_status         — can_set_task_status(task, to)
3) Execution-time правила     — from_status совпадает, комментарий, и т.п.
   (проверяются только в change_task_status)

Общая логика 1+2 вынесена в is_task_transition_allowed(task, to) —
используется и в get_task_available_transitions, и в change_task_status.
Гарантия: если get_... вернул 'allow', change_task_status с теми же
(auth.uid(), task, to) не упадёт на графе/правах.

--------------------------------------------------------------------------------
6. КОММЕНТАРИЙ
--------------------------------------------------------------------------------
- Обязателен при переходе on_review -> needs_rework (P0001, если пусто/пробелы).
- Хранится в task_status_history.comment.
- В get_task_available_transitions НЕ учитывается (это правило формы на клиенте,
  контракт: клиент показывает поле ввода перед вызовом change_task_status).
- Для остальных переходов комментарий разрешён (пишется в историю), но не обязателен.

--------------------------------------------------------------------------------
7. RPC: change_task_status
--------------------------------------------------------------------------------
Сигнатура:
  change_task_status(
    p_object_id   uuid,
    p_task_id     uuid,
    p_from_status task_status,
    p_to_status   task_status,
    p_comment     text default null
  ) returns void

Порядок проверок (важен для понятных ошибок):
  1) задача найдена по (id, object_id) — FOR UPDATE; иначе P0002
  2) from_status совпадает с БД (optimistic lock); иначе 40001
  3) is_task_transition_allowed(task, to); иначе 42501
  4) комментарий для needs_rework; иначе P0001
  5) set_config('app.allow_status_change','on',true), UPDATE, INSERT history

Принято:
- object_id в сигнатуре — guard контекста (задача должна принадлежать объекту).
- from_status в сигнатуре — optimistic lock. При несовпадении 40001.
  Клиент по 40001 делает F5 (не пытается "тихо" перезапросить).
- auth.uid() внутри, user_id НЕ передаётся параметром (нельзя подделать).
- security definer + search_path = '' — обход RLS для внутренних проверок
  и защита от подмены схемы.
- FOR UPDATE — сериализация конкурентных смен статуса одной задачи.

--------------------------------------------------------------------------------
8. RPC: get_task_available_transitions (для UI)
--------------------------------------------------------------------------------
Сигнатура:
  get_task_available_transitions(
    p_object_id   uuid,
    p_task_id     uuid,
    p_from_status task_status
  ) returns jsonb

Формат ответа (вариант C):
  {
    "expected_status": <что прислал клиент>,
    "current_status":  <актуальный статус из БД>,
    "stale":           <true, если expected != current>,
    "transitions": {
      "<status>": "allow" | "disallow",
      ... по всем значениям enum task_status
    }
  }

Принято:
- transitions считаются от АКТУАЛЬНОГО статуса (current_status), не от expected.
  => после F5 клиент сразу видит правильные кнопки без второго запроса.
- stale=true — сигнал "покажи уведомление, статус изменился".
- Переход в тот же статус всегда 'disallow' (следствие графа).
- Итерация по enum_range(null::public.task_status) — новые статусы
  подхватываются автоматически (но пары в граф всё равно надо добавлять вручную).
- Комментарий не учитывается (см. п.6).
- read-only, stable; без FOR UPDATE.
- 40001 НЕ бросается: клиент получает stale=true и актуальные transitions.

--------------------------------------------------------------------------------
9. ЗАЩИТА ОТ ОБХОДА RPC (два рубежа)
--------------------------------------------------------------------------------
1) revoke update (status) on public.tasks from authenticated, anon;
   grant update (title, description, assignee_id, object_id, updated_at)
     on public.tasks to authenticated;
   => клиент не может сделать PATCH /tasks с {"status": ...}.

2) BEFORE UPDATE OF status триггер prevent_direct_status_change:
   - падает, если status меняется вне change_task_status;
   - change_task_status выставляет локальный GUC
     set_config('app.allow_status_change','on', true);
   - GUC локальный для транзакции, не утекает в пул соединений.

security definer в change_task_status работает от владельца таблицы —
revoke на него не влияет.

--------------------------------------------------------------------------------
10. ИСТОРИЯ СТАТУСОВ (task_status_history)
--------------------------------------------------------------------------------
- Append-only: INSERT разрешён, UPDATE/DELETE запрещены триггером
  enforce_history_append_only (raise exception).
- Нет RLS-политики на INSERT для authenticated — прямой INSERT через API
  запрещён. Пишет только change_task_status (security definer).
- SELECT — через can_access_task(task_id) (manager видит всё, executor — свои).
- Первая запись (from_status = null, to_status = 'new') — при создании задачи.
  В текущей схеме триггера на INSERT tasks нет, пишется вручную в seed.
  Если добавите AFTER INSERT триггер — уберите ручную запись из seed.

--------------------------------------------------------------------------------
11. RLS (сводка)
--------------------------------------------------------------------------------
objects:
  SELECT  manager: is_manager(); executor: есть задача на объекте (assignee_id=uid)
  INSERT/UPDATE/DELETE  только manager.
tasks:
  SELECT  manager: is_manager(); executor: assignee_id = uid
  INSERT/DELETE  только manager
  UPDATE  is_manager() AND author_id = uid (сужено — manager не трогает чужие)
task_status_history:
  SELECT  can_access_task(task_id)
  INSERT  нет политики (только через security definer RPC)
  UPDATE/DELETE  нет политики + триггер
profiles:
  SELECT  свой профиль ИЛИ is_manager()
  INSERT/UPDATE/DELETE  только service_role (нет политик для authenticated)

Принято:
- RLS отвечает на "можно ли трогать строку", триггеры/функции — на
  "какой именно переход и кем".
- security definer функции используются как "внутренний API" в обход RLS.

--------------------------------------------------------------------------------
12. ОШИБКИ (SQLSTATE — контракт с клиентом)
--------------------------------------------------------------------------------
  42501  — недостаточно прав
  P0001  — нарушение бизнес-правила (недопустимый переход, нет комментария)
  P0002  — задача не найдена (в т.ч. object_id не совпал)
  40001  — serialization_failure (from_status устарел; клиент делает F5)

Принято:
- Клиент различает эти коды и по-разному реагирует (F5 / уведомление / форма).
- "Не найдено" и "from_status устарел" — РАЗНЫЕ ошибки (P0002 vs 40001).

--------------------------------------------------------------------------------
14. КОНТРАКТ КЛИЕНТ-СЕРВЕР (короткая шпаргалка)
--------------------------------------------------------------------------------
1) Клиент получает задачу (status = X) через обычный SELECT (RLS).
2) Клиент вызывает get_task_available_transitions(object_id, task_id, X).
3) Если stale=false — рисует кнопки по transitions.
   Если stale=true — показывает уведомление "статус изменился на current_status"
   и перерисовывает кнопки по transitions (второй запрос не нужен).
4) Пользователь жмёт кнопку -> клиент вызывает change_task_status(
     object_id, task_id, X, to_status, comment?
   ).
5) Ошибки:
     42501  -> "нет прав" (кнопку вообще не должны были показать — баг UI)
     P0001  -> "нужен комментарий" / "переход невозможен"
     P0002  -> "задача не найдена" (устаревший контекст)
     40001  -> "статус изменился, обновите" -> F5
6) При успехе — перечитать задачу и историю (или обновить локально).
