 # CRM для строительной компании. 
Руководитель ставит задачи по объектам (стройкам), исполнители выполняют их и отдают на проверку. 
- Аккуратный и понятный интерфейс
- Продуманная логика
- Защита данных


## Описание проекта
### В системе две роли:
 1. Постановщик - создаёт, редактирует и удаляет объекты и задачи; назначает исполнителя; принимает задачи или возвращает на доработку; видит всё
 2. Исполнитель - видит только свои задачи и объекты, в которых у него есть задачи; берёт задачу в работу и отправляет на проверку

Постановщиков и исполнителей может быть несколько.

### Объекты:
Объект — это стройка. 
Поля: название, адрес. 
В карточке объекта — список его задач со статусами.

### Задачи
Поля: название, описание, объект, исполнитель, статус, автор, дата создания.

Статусы и переходы:
| Из статуса | В статус | Кто может | Условие |
| :---- | :---- | :---- | :---- |
| — | Новая | постановщик | при создании задачи |
| Новая | В работе | назначенный исполнитель | — |
| В работе | На проверке | назначенный исполнитель | — |
| На проверке | Принята | постановщик | — |
| На проверке | На доработке | постановщик | комментарий обязателен |
| На доработке | В работе | назначенный исполнитель | — |

Каждая смена статуса сохраняется: кто, когда, из какого статуса в какой, комментарий (если есть). 
История видна в карточке задачи обеим ролям.

### Экраны
1. Вход по email и паролю.  
2. Список объектов.  
3. Карточка объекта со списком задач.  
4. Карточка задачи: данные, кнопки доступных действий, история.  
5. «Мои задачи» для исполнителя.

Интерфейс показывает только те действия, которые доступны текущему пользователю в текущем статусе задачи.


## Стек
- React на TypeScript (строгая типизация), 
- Supabase (облачный бесплатный тариф подойдёт).
- UI-библиотека - Material UI


## Требования к безопасности**
Безопасность — обязательная часть задания: в наших проектах реальные данные клиентов. Правила доступа должны работать, даже если обращаться к Supabase напрямую, в обход интерфейса.

1. Права доступа закрыты на уровне базы (RLS), а не только скрыты в интерфейсе.  
2. Исполнитель не может прочитать или изменить чужие задачи.  
3. Переходы статусов проверяются на стороне базы: запрещённый переход не пройдёт, даже если отправить запрос вручную.  
4. Историю статусов нельзя подделать, изменить или удалить через API.  
5. Открытая регистрация отключена. Тестовых пользователей можно создать вручную в Supabase.  
6. Секретные ключи (service\_role и подобные) не попадают во фронтенд и в репозиторий.
